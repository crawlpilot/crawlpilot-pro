# Column Normalization & Unification Plan

## Problem Statement
Currently, Column IDs are generated by hashing the **exact** CSS selector path.
Minor structural variations in the DOM (e.g., variable list items, ads injected in between, or flex layout shifts) cause the "same" field to have different selectors.

**Example:**
*   Row 1: `... > div (2) > flex (2) > flex alt`
*   Row 2: `... > div (2) > flex (3) > flex alt`

These produce two separate columns: "Flex Alt" and "Flex Alt (1)", rendering the table sparse and fragmented.

## Proposed Logic
We need to **normalize** the selector string *before* generating the Hash ID.

### 1. Selector Normalization Strategy
Modify `SchemaGenerator.ts` -> `generateHashId` (or the caller) to clean the key.

**Transformation Rules:**
1.  **Strip Indices**: Remove `(n)`, `:nth-child(n)`, or `[n]` patterns from the path.
    *   `div (2)` -> `div`
    *   `flex (3)` -> `flex`
2.  **Strip Generic Containers**: Can we ignore `div > div` chains? Maybe too aggressive.
3.  **Focus on Terminal**.

**Revised Algorithm:**
```typescript
function normalizeKey(key: string): string {
    return key
        .replace(/\s*\(\d+\)/g, '')  // Remove (2), (3) etc from our custom selector builder
        .replace(/:nth-child\(\d+\)/g, '') // Remove standard CSS nth-child
        .trim();
}
```
*Result*: Both examples become `... > div > flex > flex alt`. -> **Same Column ID**.

### 2. Impact Analysis
*   **Risk**: What if `flex (2)` and `flex (3)` really *are* different data? (e.g. Price vs Discount Price).
    *   Usually, if they share the same structure path *name* (like `flex`), they are likely same-type items in a list or grid.
    *   If they were distinct semantic fields, they usually have different classes or hierarchy depth.
*   **Mitigation**: We can use a "Semantic Fingerprint" fallback if available, or just rely on the fact that for "List Extraction", aligning by structure depth + tag is usually correct.

### 3. Implementation Steps

#### Step 1: Update `SchemaGenerator.ts`
Implement `normalizeSelector(key: string)` method.

#### Step 2: Use Normalized Key for ID Generation
Pass the *normalized* key to `generateHashId`.
*   Note: We still store `originalId` as the *first observed* selector for that column to allow data lookup, BUT...
*   **Critical Issue**: If Row 2 has `flex (3)` and Column calls for `flex (2)`, lookup fails.

#### Step 3: Multi-Selector Mapping (The "Merge" Logic)
Simply normalizing the ID is not enough. The `DataTable` lookup relies on `row[col.originalId]`.
If we merge `flex (2)` and `flex (3)` into Column `X`, but Column `X` thinks `originalId` is `flex (2)`:
*   Row 1 has `flex (2)` -> Match.
*   Row 2 has `flex (3)` -> No Match (Undefined).

**Solution constraint**: We need the **Row Normalization** logic (in `element-selector.ts` and `DataAggregator.ts`) to ALSO normalize the keys in the data object, OR we need the Column to support multiple `sourceSelectors`.

**Better Approach (Row-Side Normalization)**:
When extracting data (`DataExtractor` or `ElementSelector`), we should probably return keys that are *already* normalized?
*   No, `DataExtractor` tries to be precise.

**Refined Approach (Schema-Side Mapping)**:
1.  `SchemaGenerator` defines Column `X` based on `normalize(selector)`.
2.  When processing rows (in `DataAggregator` or `element-selector` normalization loop):
    *   Iterate through Row Keys.
    *   Normalize each Row Key.
    *   Match Normalized Row Key -> Column ID.
    *   Assign value.

```typescript
// Current Normalization (element-selector.ts)
columns.forEach(col => {
    if (row[col.originalId] !== undefined) {
       newRow[col.id] = row[col.originalId];
    }
});

// New Normalization Logic
Object.keys(row).forEach(rawKey => {
    const normalizedKey = normalizeSelector(rawKey); // Remove (2), etc.
    const colParams = schemaGenerator.processColumnInfo(normalizedKey); // Get ID from normalized key
    const colId = colParams.id;
    
    // Find the column definition to ensure it exists
    if (columnMap.has(colId)) {
        newRow[colId] = row[rawKey];
    }
});
```

This ensures that `flex (2)` and `flex (3)` both map to the *same* Column ID `X`, and the value is assigned correctly.
